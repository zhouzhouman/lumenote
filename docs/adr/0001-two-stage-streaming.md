# ADR 0001：采用两段式流式架构

- **状态**：已采纳
- **日期**：2026-10-11

---

## 背景

Lumenote 的核心功能是长文摘要。一篇 3万字的文章走Map-Reduce，
在 DeepSeek 上可能需要 30 秒到 3 分钟。这远超普通 API 请求的耐心预期。

同时项目选择了 Serverless 部署路线（Vercel），而 Serverless 有明确的函数执行时长上限。

---

## 决策

把「创建任务」与「消费输出」拆成两个 HTTP 请求：

```
POST /api/tasks               → 立即返回 taskId（目标 < 200ms）
GET  /api/tasks/:id/stream    → SSE 持续推送直到终态
```

管线通过 Next.js 的 `after()` 挂到响应发送之后执行。

---

## 备选方案

### 方案 A：单请求内直接流式返回

最直观，用户体验上也「最顺」——一次交互就出结果。

**否决理由**：

1. **超时**。Vercel Hobby 的函数上限约 10 秒（Fluid compute 下更长但仍有上限），
   长文任务必然被中途强杀。而**被强杀时用户已经等了几十秒却什么也没得到**，
   这是最糟的失败形态。
2. **断线即丢**。用户切走页面、网络抖动、代理超时，
   前面已经生成的 token 全部作废。钱花了，内容没了。
3. **无法重连**。没有稳定句柄标识「这个任务」，客户端无从恢复。
4. **浪费已完成的计算**。跑到 80% 被杀，纯亏。

### 方案 B：WebSocket

天然双向、能保持连接。

**否决理由**：

- 需求是单向的（服务端 → 客户端），SSE 已经够用
- Serverless 对长连接支持很差：函数在连接期间要一直占着，
  而 Serverless 的定价模型是按执行时长计费的，一个挂着不发的连接也在烧钱
- WebSocket 需要额外的路由与协议处理，在Next.js App Router 里配置更复杂
- SSE 天然走标准 HTTP，天然穿透代理与CDN

### 方案 C：外部任务队列（Trigger.dev / QStash + 独立 Worker）

最「正确」的生产架构。

**暂缓理由**：引入外部服务会让部署复杂度显著上升，
而当前项目阶段更需要先把核心链路（SSE 协议、断线重连、成本控制）跑通并验证。

**但这是注定的下一步** —— 见下方「后续」。

---

## 决策理由

两段式的核心价值不是「更快」，而是**把「计算」与「连接」解耦**：

- 计算失败 → 客户端重连即可拿到已落库的部分结果
- 连接断开 → 服务端照常算完并落库
- 服务重启 → 内容在数据库里，重连后回放

代价是多一次往返。但这一次往返是 < 200ms 的，
相比「等 60 秒然后失败」完全不是问题。

### 为什么用 `after()` 而不是 `await`

如果管线在请求内`await`，用户就得盯着一个几十秒的请求。
`after()` 让请求立刻返回，管线在响应发送完成后才开始跑，
既保证了「响应时间不受管线耗时影响」，又让管线仍有一个完整的请求生命周期。

---

## 关键细节

### 幂等是第一段的重点

POST 只做三件事然后返回，**绝不执行任何 LLM 调用**。

配合 `Idempotency-Key` 请求头与 `Task @@unique([userId, idempotencyKey])` 唯一约束，
重复点击、客户端重试、SSE 重连都不会产生第二次调用。

**对 LLM 应用来说，幂等不是优化，是止损。**
普通 CRUD 重复请求最坏是数据写两遍；LLM 重复请求**每一遍都真实花钱**。
一次长文摘要约¥0.1，一个脚本循环打 1000 次就是 ¥100。

### 第二段要处理三种情况

1. **已完成** → 整段回放已落库内容（用户中途刷新页面也能看到完整结果）
2. **已失败** → 返回错误原因与重试轨迹
3. **进行中** → 轮询数据库做增量推送

第3 种的轮询间隔是 300ms。这个间隔是权衡结果：
太小会给数据库造成不必要的压力，太大则影响流式观感。

### SSE 的三个工程坑

1. **心跳帧以 `:` 开头**（SSE 注释语法），必须跳过，否则被解析成空事件
2. **`TextDecoder` 必须 `{ stream: true }`**，否则中文/emoji 跨 chunk 边界时被截断成乱码
3. **必须发 `X-Accel-Buffering: no`**，否则 Nginx 会缓冲整个响应，流式效果完全消失

---

## 后果

**正面**：

- 响应时间与管线耗时解耦
- 断线可重连，服务重启不丢结果
- 可以展示「正在处理第 3/8 块」这类真实进度

**负面**：

- 客户端逻辑更复杂（要处理两次请求）
- 需要处理「任务已创建但客户端没连上」的情况
- SSE 有超时上限（当前实现 10 分钟），超时后客户端需要重连
  —— 已通过 `done` 事件的 `status: 'running'` 明确告知「还在跑，请重连」

---

## 后续

`after()` 仍有平台超时上限。极长文档在 Serverless 上可能跑到一半被终止。

生产环境的正确做法是迁移到外部 Worker：POST 接口只负责入队，
由 Trigger.dev / QStash 拉起独立的 Worker 执行管线，
SSE 端点从数据库轮询进度。这样执行时长不再受 Serverless 限制。

当前实现已把「管线执行」与「请求处理」完全分离，
迁移时只需替换 `after()` 里的调用为入队操作，其余代码不动。
