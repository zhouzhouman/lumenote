# ADR 0002：LLM Provider 抽象与降级链

- **状态**：已采纳
- **日期**：2026-10-11

---

## 背景

项目定位是「轻量 AI 工具集合」，摘要只是第一个功能。
后续要加翻译、写作、术语一致性校验等功能，
而不同功能对模型的要求不同：摘要要便宜，写作要好。

同时深度绑定单一厂商有风险：API 故障、限流、涨价、模型下线都会直接变成产品故障。

---

## 决策

### 1. 定义薄接口 `LLMProvider`

`src/lib/llm/types.ts` 只要求四个方法：

```ts
interface LLMProvider {
  generate(req: LLMRequest): Promise<LLMResult>;
  stream(req: LLMRequest): AsyncGenerator<StreamEvent>;
  isAvailable(): boolean;
  capabilities(): ProviderCapabilities;
}
```

### 2. 建立四级降级链

```
mock → deepseek-flash → deepseek-v4-pro → openai → heuristicSummary
```

### 3. 降级结果必须显式标记

`degraded: true`，UI 上显示「降级结果」徽章。

---

## 备选方案

### 方案 A：直接用 DeepSeek SDK 写死

最快出活。

**否决理由**：

- 一旦要加OpenAI 或换模型，抽象要临时补，届时改动面比一开始就设计好大得多
- 「降级」这件事没法做。没有抽象就没有「换一个试试」的概念

### 方案 B：完整可插拔插件系统（配置文件驱动 Provider）

最灵活。

**否决理由**：过度设计。当前只有两个真实 Provider，
配置文件驱动的动态加载会引入「运行时才知道配错了」的失败模式 ——
而这类错误在生产环境发现时往往已经浪费了钱。

### 方案 C：直接用 Vercel AI SDK 的默认多 Provider 支持

AI SDK 本身已支持 `fallback()`。

**考虑过**，但它提供的是「模型级 fallback」，
而我们需要的是**跨厂商降级 + 本地兜底 + 成本感知**，
且需要在降级时记录轨迹（给 UI 展示「为什么变慢了」）。
自己在 `LLMProvider` 这一层实现更可控。

---

## 决策理由

### 接口为什么这么薄

抽象层越薄，越容易在厂商特性变化时**绕过它直接修适配器**。

抽象层厚的典型后果是：所有厂商都被迫实现它们用不上的方法，
于是接口里出现 `supportsVision(): boolean` 这种只有一个厂商返回 true 的东西，
半年后没人记得它是干嘛的。

当前四个方法已经覆盖了实际需要，且都不会因为新功能而膨胀。

### 降级顺序为什么这样排

```
mock               无网络依赖，永远可用（用于开发与预览环境）
deepseek-flash     主力：便宜、快，摘要场景足够
deepseek-v4-pro    同厂商内升级：语义一致，降级后风格不突变
openai             跨厂商兜底：DeepSeek 整体故障时用
heuristicSummary   本地：抽取式摘要，**保证用户永不看到空白**
```

**同厂商优先于跨厂商**，因为换厂商可能让输出风格突变（标点习惯、段落结构、语气），
用户会明显感觉「这次结果不一样」。先在同厂商内升级能把风格变化降到最低。

最后一档 `heuristicSummary` 是抽取式的（基于句子权重挑选原文关键句），
质量远不如 LLM，但**它的存在意义是「不返回空白」**。
一个空白页面会让用户以为服务挂了，然后离开。

### 为什么降级必须标记

不标记等于欺骗用户。

用户以为拿到的是模型输出，其实是本地字符串拼接。
一旦发生降级却没告知，产品的可信度就毁了 ——
而且用户很可能会在下一次发现质量下降时失去信任，且我们无从解释。

### 可靠性四层的关系

```
重试（retry.ts）      瞬时故障：429、5xx、网络抖动
   ↓ 仍然失败
熔断（breaker.ts）    持续故障：快速失败，不再浪费尝试
   ↓ 熔断打开
降级（service.ts）    换模型 / 换厂商
   ↓ 全部不可用
兜底（budget.ts）     本地启发式，页面绝不空白
```

**只对 retryable 错误重试。**
参数错误（400）和内容过滤重试没有意义 —— 结果必然一样，只是白烧 token。

### 退避为什么用全抖动

固定指数退避（2s/4s/8s）有个致命问题：
所有被限流的客户端会在**同一时刻**一起重试，形成第二波脉冲（thundering herd），
把刚恢复的服务again 打挂。

全抖动 `random(0, min(cap, base * 2^n))` 把请求摊平到整个窗口内。
这是 AWS Architecture Blog 的经典结论。

### 一个诚实说明：熔断器状态在内存里

`breaker.ts` 的状态存在进程内存，Serverless 多实例部署下**不共享**。

单实例部署没问题，多实例时熔断判断会不准。
正确做法是换Redis。但这在当前部署形态下是可接受的取舍 ——
已在代码注释与 README「已知限制」里明确写出，不隐瞒。

## 关键细节

### 厂商特性必须走 `providerOptions`

DeepSeek 特有的 `thinking`、`response_format` 不能塞进通用参数：

```ts
providerOptions: {
  deepseek: {
    thinking: { type: 'enabled' | 'disabled' },
    response_format: { type: 'json_object' },
  },
}
```

塞进通用参数的后果是：切到OpenAI 时这些参数会被发过去并报错。
**厂商特性必须隔离在适配器内。**

### usage 的缓存字段需要多路兜底提取

不同厂商（或同一厂商的不同版本）返回usage 的字段名不一致：

```
cachedInputTokens / cacheHitInputTokens / promptTokensDetails.cachedTokens
```

适配器里做多字段兜底，避免某天厂商改名导致成本统计静默失效 ——
**成本统计失效不会报错，只会让账单悄悄离谱。**

---

## 后果

**正面**：

- 换厂商 / 加功能时改动面小
- 单个厂商故障不会导致产品不可用
- 成本可按模型分别统计，能发现「高级模型被误用」这类早期信号

**负面**：

- 抽象层带来一定的间接层复杂度
- 降级链的顺序需要根据实际故障经验调整，不可能一次配对

---

## 后续

- 熔断器与限流迁到 Redis（多实例部署时）
- 降级链支持按用户等级 / 任务类型配置不同顺序
  （比如摘要走便宜模型，写作直接上 pro，不做无谓降级）
