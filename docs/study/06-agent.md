# 06 · Agent 子循环：多轮工具调用

> 目标：能回答"为什么不能用一个函数搞定""工具怎么防滥用""预算怎么兜底"。

---

## 1. 与普通管线的区别（一句话）

普通管线是"输入 → 一次或多次调用 → 一段文本"；
Agent 是"输入 → **多轮工具调用** → 结论 + 轨迹"。复杂度从"分块策略"转移到"循环控制、预算、轨迹持久化"。

**为什么不合并成一个函数？**
注释写得很直白：硬塞进去的结果是两边的最坏情况都要考虑
（比如"分块 + 工具调用"这种组合没有任何意义，却要实现处理它）。

**Agent 的降级链只取第一项**：不在循环外面套"换 provider 重跑整个任务"，
否则已经花掉的工具调用和 token 会被重复消耗。

---

## 2. 循环状态机

```
        ┌───────────────────────────────┐
        ▼                               │
   [预算检查] ──超限──▶ 收敛调用（不带 tools）──▶ give_up
        │                               │
        ▼                               │
      plan ──无 toolCalls──▶ finalize（succeeded）
        │
        ├─有 toolCalls─▶ act（dispatch）
        │                   ├─ 重复 2 次 → warn（注入提示）
        │                   ├─ 重复 3 次 → stop（强制收敛）
        │                   └─ 工具额度用尽 → stop
        ▼
     observe（记录 span）──▶ 回到预算检查
```

**控制权在代码手里**：模型只在 `plan` 阶段决定"调哪个工具"或"给结论"，
循环的终止、收敛、额度都由代码判定。

## 3. 工具清单与按工具额度（`agent/tools.ts:38-66`）

| 工具 | 作用 | 额度 |
|---|---|---|
| `list_sections` | 列出每块首个 Markdown 标题 + 80 字预览（建立全局观） | 2 |
| `search_chunks` | 关键词检索，按命中词数降序、摘录 600 字 | 10 |
| `fetch_url` | 抓网页 → 分块并入索引，**只回前 500 字预览** | 3 |
| `get_glossary` | 术语表双向往返匹配，最多 10 条 | 5 |
| `diff_with_task` | 与历史任务输出做行级 diff，只回相似度 + 20 行样本 | 3 |

**为什么要按工具分额度？**
全局 20 步约束不了"20 步里调 20 次 `fetch_url`"，而它是最贵、唯一触网的操作。

**安全性是结构性的**：只注册**只读**工具，模型物理上没有写能力。
未知工具名在调度层直接拒绝（`quota === undefined`），杜绝绕过白名单。

**工具执行永不抛异常**：所有错误转成 `{ok:false,error}` 作为观察结果回给模型，
让模型自己决定换关键词还是换路。抛异常会打断循环，损失已得信息。

## 4. 参数校验的真实状况（可以主动说）

| 层 | 做了什么 |
|---|---|
| 声明 | 给模型的 JSON Schema：`additionalProperties:false`、`required`、`topK` 标 `minimum/maximum` |
| 白名单 | 工具名不在额度表 → 拒绝，不执行 |
| 类型收窄 | 每个 case 手写 `typeof args.x === 'string' ? ... : ''` |
| 领域约束 | 空 query 直接失败 |
| 重复检测 | 参数**键排序后**序列化，避免 `{a,b}` 与 `{b,a}` 被当成两次 |

**缺口**：项目没有用 zod 做统一的运行时校验；`topK` 的 `maximum:10` 只是给模型看的提示，
服务端只做 `Math.max(1, topK)`，模型传 100 不会被截断。

## 5. 预算：步数优先于 token

| 维度 | 上限 | 计数点 | 超限 |
|---|---|---|---|
| 步数 | 默认 12（可选 6/12/20，**硬夹 30**） | **仅 plan 阶段的调用** | `stopReason='max_steps'` → 收敛 |
| token | 60,000 | 所有调用（含缓存命中的输入） | `max_tokens` → 收敛 |
| 成本 | **循环内没有闸门** | 结束后聚合成一条 `UsageLog` | 只记账，不中断 |

```ts
// budget.ts:107-111
exhaustedReason() {
  if (steps >= maxSteps) return 'max_steps';    // 步数优先，保证 stopReason 确定
  if (tokens >= maxTokens) return 'max_tokens';
  return null;
}
```

**硬夹 30 的意义**："即使数据库被改成 10000，也不能让一次任务跑一万轮"。

**收敛调用不占步数**：否则预算到顶时反而没预算做收敛，永远拿不到部分结果。
收敛调用**刻意不传 tools**，确保模型只能输出文本。

四种收敛原因各有专属文案（`max_steps` / `max_tokens` / `repeat_loop` / `tool_quota`）：
**知道为什么被中断，才能给出恰当的局限性说明。**

## 6. 轨迹落库（`AgentStep`）

```
onStep(step) ── void persistStep(step) ──▶ create(AgentStep)
                 │ 失败/唯一冲突 → 只打日志，不中断任务
                 └─ **写库成功后才** onStep?.(step) → SSE 推送
循环不等待写库（避免 12 步多出几百 ms）
         ▼
   await flushSteps()   // 显式追踪 pending 写，不能用 setTimeout(0)
```

| 机制 | 原因 |
|---|---|
| `@@unique([taskId, seq])` | 重跑时忽略重复那一遍 |
| 写库失败不中断 | "为了记日志而让用户拿不到结论，是把优先级搞反了" |
| 先落库再推 SSE | 否则刷新页面后"刚看到的那一步不见了" |
| `flushSteps()` 显式等待 | `setTimeout(0)` 只让出微任务轮次，不保证 IO 完成 |

## 7. 证据校验（`agent/evidence.ts`）

```ts
if (content.includes(quote)) verified++;                              // 精确
else if (normalize(content).includes(normalize(quote))) verified++;    // 归一化兜底
else missing.push({...ev, reason: '引用的原文片段未在该分块中找到'});
```

| 解析 | 正则 `chunk\s*[:：#]?\s*(\d+)`，容错 `chunk:12` / `chunk#12` / `chunk 12` |
| 失败原因 | 无法解析 / 分块不存在 / quote 为空 / 匹配不上（四种） |
| 失败后果 | 结论**照常展示**，只降 rate；rate 写进 trace span 与 UI 徽标 |

**为什么不叫"正确性校验"？**
"结论对不对"需要领域知识；"有没有依据"可以零成本、确定性地判定。
这个拆分本身就是设计能力。

**局限**：UI 不展示"引文是否真能在原文找到"，DB 也不保存分块，所以事后无法复核。

## 8. 追问（followup）：为什么只带上一轮

```ts
const context = [
  '<previous_result>', parent.outputContent, '</previous_result>',
  '<question>', question, '</question>',
].join('\n');
```

| 决策 | 理由 |
|---|---|
| 只带父任务结果 + 本轮问题 | DeepSeek 输出价约为输入 4 倍，全历史成本随轮次线性增长 |
| 不带原文 | 追问的是结论（"第二点展开"），带原文会让模型重新摘要，更贵且答非所问 |
| 沿用父任务的模板/参数 | 保证风格一致 |
| **不写幂等键** | 多轮交互，同一问题问两次就该跑两次 |
| 强制单次调用不分块 | 上下文比原文短且需要完整上下文 |

**成本闸门必须有**：早期漏了配额检查 = 给免费用户开了一条无限追问的烧钱通道。

GET 侧支持 `?whole=1`：沿 `parentTaskId` 向上找根（深度上限 50 防环），再从根 BFS 展开。

## 9. 输出解析的容错（`agent/output.ts`）

三级候选依次 `JSON.parse`：
1. ` ```json ` 代码块
2. 第一个 `{` 到最后一个 `}`
3. 整段文本

全失败返回 `null`，展示退回纯文本。`extractDisplayText` 剥掉 JSON 块，剥完为空则**原样返回**
——"宁可多显示一段 JSON，也不能让用户面对一片空白"。

## 11. 面试问答

**Q：Agent 和普通摘要的本质区别？**
> 普通管线是"一次（或 Map-Reduce 若干次）调用出文本"；Agent 是"多轮决策 + 工具调用"。
> 复杂度的位置不同：前者在分块与合并，后者在循环控制、预算、轨迹持久化。
> 所以我没有合并成一个函数——那会让两边的最坏情况都要考虑，而"分块+工具调用"这种组合没有意义。

**Q：模型乱调工具怎么办？**
> 四道：① 只注册只读工具，物理上没有写能力；② 按工具分额度（`fetch_url` 只有 3 次，
> 因为它唯一触网、最贵）；③ 参数序列化后做重复检测，第 2 次警告、第 3 次强制收敛；
> ④ 未知工具名在调度层直接拒绝。

**Q：预算到顶了怎么还能给出结论？**
> 有一次"收敛调用"：不传 tools、明确告知停止原因，要求基于已检索到的内容给结论。
> 这次调用不占步数，否则预算到顶就没有预算做收敛。最终任务标 `succeeded + degraded`，
> 而不是 failed——部分结论比没有结论有用。

**Q：怎么防止模型编造引用？**
> 不做"正确性判断"，做"依据校验"：解析 `chunk:N` → 在该块里精确匹配 quote，
> 不行就归一化（去空白、统一标点、小写）再匹配。匹配不上就计入 missing 并降低 rate。
> 结论照常展示，但 UI 会标"N 条无证据"。这个检查零成本、完全确定性，不需要 LLM 判官。
