## A. 架构与设计决策（8）

**A1. 用一句话介绍这个项目。**
> 一个可自托管的 AI 文本工作台：摘要/翻译/润色 + 批量处理 + 审计留痕。
> 核心不是"调模型"，而是**把不可控的模型调用变成可控的成本、可追溯的结果、可降级的服务**。

**A2. 为什么提交任务不直接返回结果？**
> 一次调用可能几十秒，长文更久。所以两段式：POST 只落库（可幂等、可审计），
> 执行挂 `after()`，结果用 SSE 订阅。代价是 `after()` 不是真队列，进程重启会丢。

🔁 **那为什么不用消息队列？**
> 因为要额外运维 Redis/BullMQ。现阶段是演示级，README 里把"换真队列 + reaper"列为已知缺口。

**A3. 三层架构怎么划分的？**
> API 层只管校验与落库（不调模型）；管线层管分块与编排；LLM 层管可靠性（重试/熔断/降级/计量）。
> 横切三块：guardrail（输入包裹/输出脱敏）、metering（计费）、audit（留痕）。

**A4. 如果让你重做，哪三件事会不一样？**
> ① 一开始就用真队列，而不是 `after()`；
> ② SSE 直接推 token（现在是轮询 DB + 终态回放）；
> ③ 熔断器状态机写完整（现在 `recordSuccess` 不回 CLOSED）。

**A5. 这个项目最难的技术点是什么？**
> 不是调模型，是"**失败时的语义**"：分块失败要不要中断、预算超了算不算失败、
> 审计写失败要不要让业务失败、取消是立即还是协作式。每个选择都牵扯成本与用户体验。

**A6. 为什么要区分 SecurityEvent 和 AuditLog？**
> 前者是认证侧（谁试图登录、失败几次），后者是业务侧（谁跑了批次、导出了什么）。
> 混在一起会让"登录失败刷屏"淹没"有人导出了全部数据"这种真正要报警的事件。

**A7. 数据库为什么没有用 enum 表示状态？**
> 改 enum 要 `ALTER TYPE`，在快速迭代的迁移节奏里成本高。代价是合法性只由应用保证。

**A8. 单用户并发为什么限制成 1？**
> 保护用户自己的钱（BYOK）不被多标签页烧掉，也让"预算闸门"有意义。
> 只数近 10 分钟的 `queued/running`，避免历史卡死任务永久占位。

## B. LLM 可靠性（10）

**B1. 模型超时了会怎样？**
> `classifyError` 判 `TIMEOUT`（retryable）→ 同档退避重试 3 次 → 换模型 → 全挂则本地规则摘要 + `degraded=true`。

**B2. 重试为什么用全抖动？**
> 上游故障时所有客户端会同时重试形成尖峰。全抖动把重试点随机撒在 `[0,min(8s,500·2ⁿ))`，
> 上游看到平滑压力。`maxAttempts=3` 是 1 次首调 + 2 次重试。

**B3. 哪些错不重试？**
> 401/403（重试还是错）、402（钱不够）、400（请求本身错）、内容过滤。
> 这张表是可靠性的总开关，写错一个就是白烧钱或该重试的不重试。

**B4. 熔断和重试的区别？**
> 重试=这一次再试几次；熔断=这一段时间别再试。没有熔断，100 个请求 ×3 重试 = 300 次打一个挂了的服务。

**B5. 熔断阈值？**
> 连续 5 次失败，或 60s 窗口内 ≥10 次请求且错误率 ≥50% → 开 30s；
> 半开状态只放 1 个探针，探针失败冷却翻倍到 60s。

🔁 **粒度是什么？为什么？**
> `provider:model`。只按 provider 记会让 flash 熔断时 v4-pro 也被跳过——"降级链看着四层实际三层"。

**B6. 降级是怎么做的？**
> 从 prompt 里剥出正文（砍尾部指令、去标签、丢参数头），然后规则摘要：
> 句子打分（位置 + 含数字 + 关键词）→ 按原文顺序重排 → 用户要 3 条就给 3 条编号列表。
> 标 `degraded=true`，usage 全 0。

**B7. 降级的取舍？**
> 质量明显差，但用户拿到"有内容 + 明确标记"，而不是红字报错。**部分结果 > 无结果**。
> 但不能假装它是正常结果 —— 所以 `degraded` 会一路透到 UI 和导出文件。

**B8. 成本怎么算？**
> 三档：输入分缓存命中/未命中（flash 差 50 倍）、峰谷 2 倍（北京 9-12 & 14-18 的工作日）、
> 输出单独价。未知模型按 $1/1M 高估，绝不按 0（按 0 会让仪表盘失真）。

🔁 **峰谷有什么坑？**
> 必须用**北京时间**判周末。早先多加一道 UTC 周末判断，导致北京周一早高峰被判非高峰，成本低估一半。

**B9. 为什么库里只存美元？**
> 历史上三处硬编码 `*7.2` 导致详情页与仪表盘差 7.2 倍。现在统一存美元，展示时才换算。

**B10. 一个任务的用量怎么保证只有一条？**
> `UsageLog.taskId @unique`，撞 P2002 返回 `skipped:true`。Map 阶段的调用写 `taskId:null`，
> 最终成本以 Reduce 那次为准。

## C. 管线与分块（8）

**C1. 长文怎么处理？**
> 切成 1200 token 的块（重叠 100），3 路并发 Map（每块出几条要点），再 Reduce 合并。
> 成本随长度线性，不是平方。

**C2. 为什么要重叠？**
> 分块会切断跨块语义。重叠让下一块看到上一块尾巴。多花约 8% token，
> 但落在前缀缓存里（命中价是未命中的 1/50），净成本接近零。

**C3. 为什么不用 `Promise.all` 全并发？**
> 100 块就 100 个并发请求，打爆上游配额和连接池。用固定 worker 池 + 共享游标，最多 3 个在飞。

**C4. Map 的预算怎么分？**
> `floor(4000·0.8/n)`，够 5 条就不降级，不够就 `max(3, per/40)` 条并标降级。
> 关键是下限不能突破 `fairShare`，否则 100 块 × 120 token = 预算的 3 倍。

**C5. 单个分块失败会中断整批吗？**
> 不会。调用层失败是"返回降级文本"而不是抛错，所以那块变规则摘要，其余正常。
> 但这个降级只记 `UsageLog.meta`，任务级 `degraded` 反映不出来。

**C6. Prompt 变量渲染的优先级？**
> 用户值（trim 非空）> 变量默认值 > 必填抛错 > 空串。模板里有但定义里没有的变量会被替换成空串。

**C7. system prompt 为什么要单独渲染？**
> 早先原样透传，模型收到字面量 `{{style}}`，用户选项全程无效。现在渲染一次、所有分块复用，
> 而且刻意剔除 `content`——否则 system 每次都变，前缀缓存全失效。

**C8. 怎么防止 prompt 注入？**
> 正文包进 `<document>`，并把正文里的 `</document>` 换成全角防提前闭合；
> 输出侧 6 类敏感串（sk-/AKIA/gh_/Bearer/身份证/卡号）替换成 `[已脱敏]`；
> 日志只打指纹 `{length,hash}`不打印原文。
> 刻意**不做**"命中注入关键词就拒绝"——讨论安全的文档会被大量误伤。

## D. 认证与安全（12）

**D1. 登录流程？**
> IP 限流 → 账号限流 → 失败锁定（账号 5/IP 15，15 分钟）→ 查库 + bcrypt(12) 比对。
> 锁定判断必须在查库之前，否则"被锁"本身就是账号存在的信号。

**D2. 怎么防时序攻击？**
> 用户不存在时用**真实算出来的** DUMMY_HASH 做 `compare`，耗时与真实比对一致。
> 手写一个"看起来像哈希"的串会被 bcryptjs 在长度校验处短路，compare 0ms，防护静默失效。

**D3. 签发什么 token？**
> access：JWT HS256，payload 只有 `sub`，15 分钟；refresh：32 随机字节 base64url（不是 JWT），7 天，库里只存 SHA-256 hex。

🔁 **为什么 refresh 不用 JWT？**
> JWT 不能撤销。refresh 要能撤销（登出/盗用），所以必须落库比对。

**D4. 刷新怎么轮换？**
> 事务里 `deleteMany({id, refreshHash})` 看 `count===1` 才创建新行。
> 用 `deleteMany` 而不是 `delete`：并发刷新时后者抛 P2025 → 500，现象是"偶发 500，刷一下又好"。

**D5. 有重放检测吗？**
> **没有**。轮换后旧行被物理删除，旧 token 再来与"乱编 token"走同一分支。
> `destroyAllSessions` 有定义但**无调用点**。真正的 BCP 做法是保留 `reusedAt` 标记 + 撤销整个 family。

**D6. Cookie 怎么设的？**
> `httpOnly` + `sameSite=lax` + `secure` 按 APP_URL 协议推断 + **不设 domain**（host-only）。

🔁 **为什么不是生产就加 Secure？**
> 内网是 `http://192.168.x.x`，浏览器只在安全上下文接受 Secure Cookie，会被**静默丢弃**，
> 表现为"登录 200 但页面未登录"。这是真实事故。

**D7. 越权怎么防？**
> 查询层就带 userId：`findFirst({id,userId,deletedAt:null})`，查不到统一 404。
> 不用"findUnique 再比对"——那是把安全放在应用层，忘一次就是数据泄漏。

**D8. 四种限流/限额别混？**
> 限流（挡脚本，内存/Redis，可丢）、失败锁定（挡撞库，DB）、幂等（防重复花钱，唯一索引）、
> 配额/并发（防超额，DB 计数）。**前两个可以丢，后两个丢就是事故。**

**D9. 限流为什么内存也能用？**
> 丢了只是少挡几次；多实例要精确就用 Redis（Lua 保证 INCR+PEXPIRE 原子）。
> 失败模式默认 `open`：主后端挂了回退进程内存，业务不中断。

**D10. 幂等怎么实现的？**
> 客户端传 `Idempotency-Key`，清洗后落成 `(userId, idempotencyKey)` 唯一约束。
> 命中直接返回 `replayed:true`；并发双写撞 P2002 再回查。**正确性靠 DB，缓存只做优化。**

**D11. 配额为什么 BYOK 不受限？**
> 费用是用户自己付的。所以先取凭证再决定要不要查配额——顺序反了会出现"用自己的 key 却被站点额度拦住"。

**D12. SSRF 怎么防的？**
> 四层：协议白名单（http/https）→ 端口只 80/443 → 主机白名单（可配）→
> DNS 解析后**所有** IP 逐个判内网（RFC1918/环回/CGNAT/云元数据 169.254.169.254 等）。
> IP 用整数区间比较防 `0x7f.1` 绕过；校验过的 IP 通过自定义 lookup **钉进连接层**防 DNS 重绑定；
> 重定向每跳重新校验，最多 3 跳。

## E. 数据模型与事务（6）

**E1. 一句话讲 Task 表的关键设计。**
> `(userId, idempotencyKey)` 唯一 → 幂等；`status` 是 String；`promptVersionId` 快照 → 可追溯；
> `deletedAt` 软删；`inputMeta/params/outputMeta` 用 JSONB 存上下文。

**E2. 为什么要存 `promptVersionId` 而不是版本号？**
> 版本号会随模板更新漂移；存 id 能定位到"当时那段确切的 prompt"。
> 术语表也在**创建时**快照进 `params.glossary`，否则改术语表会让历史任务不可复现。

**E3. 哪些外键用了 SET NULL，为什么？**
> `Task.batchId`（批次是组织维度，任务结果有价值）、`AuditLog.userId`（删号后日志必须留）、
> `SecurityEvent.userId`。其余多用 CASCADE。

**E4. 删除用户会删除什么？**
> 会话、任务（含用量、步骤）、凭证、分享链接会级联删；审计与安全事件保留（userId 置空，靠邮箱快照）。

**E5. 事务用在哪？**
> 刷新 token 轮换（deleteMany + create）、验证码作废旧码+写新码、凭证激活（先取消其他 active）。

**E6. JSONB 字段的代价？**
> 不能建约束、查询要用路径表达式、类型安全靠应用层 cast。
> 换来的是"输入元数据/参数/输出元数据"这类结构多变的信息不用频繁迁移。

## F. 批次与审计（6）

**F1. 批次状态怎么定的？**
> 结束后用 `groupBy(status)` 数出来反推，不是边跑边累加。取消走 forced 分支优先，
> 绝不被"有几条成功了"覆盖成 partial。

**F2. 为什么串行？**
> 预算闸门"花到上限就停"，并发时闸门在起跑瞬间失效。加上本来就有单用户并发 1 的约束。
> 提速正确做法是分片 + 每片独立预算。

**F3. 预算是硬上限吗？**
> 不是，是**软上限**。闸门用预估成本，真实值只有跑完知道。实测预算 ¥0.0025 花了 ¥0.0029。
> 最坏是超最后一条的偏差，不会级联。做硬上限要预留 20% 余量，会把可用预算越压越少。

**F4. "跳过"和"失败"为什么必须分开？**
> 跳过没花钱、失败花了钱。混在一起失败率失真，用户会去排查不存在的模型问题。

**F5. 审计为什么不可篡改？**
> 数据层：`userId` SET NULL + `actorEmail` 快照、无 updatedAt/deletedAt；
> 应用层：不提供任何改删接口。但严格说只能做到应用层——有 DB 写权限还能改行，
> 彻底方案是独立账号只授 INSERT 或 WORM。

**F6. 审计的 meta 怎么防止泄漏密钥？**
> 键名黑名单递归剔除（password/secret/token/apiKey/authorization/cookie/验证码）+ 截断 200 +
> 数组只留标量。导出会给外部审计方，所以这一层不能靠自觉。

## G. Agent（6）

**G1. Agent 和普通管线区别？**
> 普通是"一次或 Map-Reduce 若干次 → 文本"；Agent 是"多轮决策 + 工具调用 → 结论 + 轨迹"。
> 复杂度从分块转移到循环控制、预算、轨迹持久化。

**G2. 工具怎么防滥用？**
> 只注册只读工具（物理上没有写能力）；按工具分额度（`fetch_url` 只有 3 次）；
> 参数序列化后重复检测（2 次警告、3 次强制收敛）；未知工具名直接拒绝。

**G3. 预算到顶怎么办？**
> 一次"收敛调用"：不传 tools、告知停止原因，要求基于已有内容给结论。这次调用不占步数。
> 任务标 `succeeded + degraded`，不是 failed。

**G4. 轨迹怎么落库？**
> 每步一行 `AgentStep`，`@@unique([taskId,seq])`；循环不等写库（避免 12 步几百 ms），
> 但显式 `flushSteps()` 收尾；**先落库再推 SSE**，否则刷新后那一步不见了。

**G5. 引用怎么校验？**
> 解析 `chunk:N` → 在该块精确匹配 quote → 不行就归一化（去空白、统一标点、小写）再匹配。
> 失败计入 missing 并降 rate，但结论照常展示。

**G6. 追问为什么不带全历史？**
> DeepSeek 输出价约为输入 4 倍，全历史成本随轮次线性涨；而且追问的对象是结论，
> 带原文会让模型重新摘要，更贵且答非所问。

## H. 测试与工程化（8）

**H1. 单测和集成怎么分工？**
> 单测覆盖 `src/lib` 纯逻辑（毫秒级），集成覆盖路由/SSE/事务/越权（真库 + 真 next dev）。
> 覆盖率只统计 lib，注释里明说"不要当成集成路径已覆盖的证据"。

**H2. 集成测试怎么保证可重复？**
> globalSetup：库名必须含 test 才许 DROP SCHEMA → migrate deploy → seed → next dev → 轮询 health。
> 还校验实例新鲜度（uptime 异常大 = 旧进程）、强制 MOCK 且把真实 key 置空串。

**H3. 覆盖率阈值怎么定的？**
> 按基线向下取整的"防倒退"值（41/82/71/41）。新代码拉低了就补测试，不是降阈值。

**H4. CI 有几个 job？**
> 六个：verify（含 build）、integration（pgvector 镜像）、rate-limit-redis、coverage、
> dependency-review、secret-scan。

**H5. Dockerfile 几个 stage？各自的坑？**
> 五个：base/deps/builder/migrator/runner。
> 坑一：动态 import 的 nodemailer 可能没进 standalone（用 outputFileTracingIncludes 兜）。
> 坑二：migrator 跑 seed 需要 `prisma generate`（migrate deploy 不需要，最容易漏）。

**H6. 怎么判断"镜像里的代码是不是最新的"？**
> 重跑 `docker compose build app`，全部 CACHED + 秒级完成就说明没有漂移。
> 比看时间戳可靠（squash merge 后 commit 时间会晚于构建时间）。

**H7. compose 的环境变量为什么容易漏？**
> `environment` 是白名单，新变量不显式列出就不会进容器。表现是"`.env` 里配了，`printenv` 是空的"。
> 而且它只读 `.env`，不读 `.env.local`。

**H8. 一次上线后功能 500，你怎么查？**
> ① `docker logs` 看错误码（配置类错误现在会透出，如 `TEMPLATE_MISSING`）；
> ② `compose exec app printenv` 与 `.env` 核对；
> ③ `build` 是否全部 CACHED（不是 → 跑的是旧镜像）；
> ④ 再不行就 `compose run --rm migrate` 看迁移是否落后。

## I. 开放题（面试官最爱，4）

**I1. 这个项目最大的不足是什么？**
> 执行器是 `after()`，不是队列 —— 进程重启会留下永久 `queued/running` 的任务，
> 而且没有 reaper。这是"能不能交给别人长期跑"的分界线。

**I2. 如果流量涨 100 倍，哪里先崩？**
> ① 并发上限 1 会让排队变长（但不会崩，这是保护）；
> ② `after()` 会让所有任务挤在 web 进程里，内存与连接池先撑不住 → 必须拆 worker；
> ③ 限流如果还是内存驱动，多实例会各算各的 → 必须切 Redis；
> ④ 数据库 `Task` 表增长最快，历史列表要 keyset 分页（已经做了）。

**I3. 你怎么衡量"摘要质量"？**
> 项目里有评测框架（`src/lib/eval`）：数据集 + 断言 + 判官 + 校准。
> 但我的看法是：**先量"可确定性"的部分**——引用命中率、格式合规率、降级率、P95 延迟、单位成本；
> 主观质量用 LLM judge 但必须和人工标定做一致性校准（`JudgeCalibration` 表就是干这个的）。

**I4. 如果只能保留一个功能，留哪个？**
> 留"可追溯 + 可降级"这条链路，而不是某个具体能力。
> 摘要谁都能做，但"成本可预测、失败有兜底、结果能审计"才是这个项目的差异点。
